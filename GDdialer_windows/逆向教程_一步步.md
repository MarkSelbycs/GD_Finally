## 第 2 步：抓包——看它到底说了什么

**目的**：日志告诉你"发了什么请求"，抓包告诉你"**报文长什么样**"。

### 2.1 用 pktmon 抓包

```powershell
# 清掉旧过滤器
pktmon filter remove

# 只抓门户端口
pktmon filter add -p 7001

# 开始抓（--pkt-size 0 = 抓完整包）
pktmon start --capture --pkt-size 0 --file-name cap.etl
```

**另开一个窗口**触发一次拨号（重启客户端 / 断开重连），然后：

```powershell
pktmon stop
pktmon etl2pcap cap.etl -o cap.pcapng
```

### 2.2 为什么用 pktmon 而不是 Frida

目标的服务进程（`ESurfingSvr.exe`）**生命周期极短**，Frida 经常报
`RtlCreateUserThread returned 0xc000010a`（进程正在退出）。

**pktmon 在网络层抓包，不依赖进程**，稳定得多。这是踩坑总结出来的经验。

### ✅ 第 2 步的产出

`cap.pcapng` 文件。

## 第 3 步：解析抓包，找出规律

**目的**：从二进制包里把 HTTP 请求/响应提出来，找出**可以推理的规律**。

### 3.1 为什么不能直接搜

body 会**跨多个 TCP 段**，第一段只有 HTTP 头。必须**重组 TCP 流**。

### 3.2 写解析脚本

见归档里的 [`re/tools/tcp_reassemble.py`](re/tools/tcp_reassemble.py)。
核心逻辑：

```python
# 1. 遍历 pcapng 的 block，取出每个以太网帧
# 2. 逐帧找 IPv4 头（pktmon 的帧前面可能有额外头，所以是"扫描"不是"固定偏移"）
# 3. 按 (源IP, 源端口, 目的IP, 目的端口) 分组，按 TCP seq 排序拼接
# 4. 从拼接后的流里找 "POST " / "GET "，按 Content-Length 切 body
```

运行：

```powershell
python tcp_reassemble.py cap.pcapng
```

### 3.3 分析 body 的规律（★ 关键思路）

拿到 5 个请求的 body 后，**不要急着解密，先做统计**：

```python
bodies = {"ticket":..., "keep":..., "auth":..., "state":..., "term":...}

# 规律 1：长度
for n,b in bodies.items():
    print(n, len(b), len(b) % 8, len(b) % 16)
```

本项目看到：

```
ticket 376 0 8      ← 都是 8 的倍数！
keep   392 0 8
auth   304 0 0
state  248 0 8
term   272 0 0
```

**推论：可能是 8 字节分组的密码。**

```python
# 规律 2：公共前缀
import os
n = 0
while all(b[n] == bodies['ticket'][n] for b in bodies.values()):
    n += 1
print("公共前缀", n, "字节")
```

看到 **48 字节** —— 正好是 `<?xml version="1.0" encoding="UTF-8"?><request><` 的长度。

**推论：body 是"加密后的 XML"，开头明文相同所以密文也相同。**

```python
# 规律 3：块级共享（判断是不是位置无关的分组密码）
# 找 keep 和 term 之间，偏移若干块后完全相同的部分
```

本项目发现 `keep[264:392] == term[144:272]`（**偏移 120 字节，共 128 字节**）。

**推论：**
- 偏移 120 = 15×8 是 8 的倍数，但 120 = 7.5×16 **不是** 16 的倍数
- **→ 分组长度是 8 字节**（不是 16）

> 💡 **这一步是整个逆向最重要的一次推理**。不用解密，光靠统计学就定下了"8 字节分组密码"。

### ✅ 第 3 步的产出

- 5 个请求的完整 body（十六进制）
- 结论：**8 字节分组、分组位置无关（ECB 类）、明文是 XML**

## 第 4 步：找可疑数据，反汇编找解析函数

**目的**：抓包时常会看到**非 HTTP 的奇怪响应**，那往往是"密钥交换"。

### 4.1 发现可疑数据

本项目在响应里发现：

```
001@6ADD6889806FF9C9E0E6E95487A73F9064FEC817537CF22184303CEAA9B27EA8$E9747EF1-6849-4F87-957B-3B93E6A90393]...
```

结构像 `001@<64位hex>$<UUID>]<载荷>`。**64 位 hex = 32 字节 = 一个密钥！**

### 4.2 写反汇编小工具

不用 IDA，用 capstone 写脚本按需反汇编：

```python
import struct
from capstone import Cs, CS_ARCH_X86, CS_MODE_32
from pathlib import Path

b = Path("ESurfingSvr.exe").read_bytes()
IB = 0x400000

# ---- 第一步：解析 PE 节表，建 VA <-> 文件偏移 映射 ----
pe = struct.unpack_from('<I', b, 0x3c)[0]
nsec = struct.unpack_from('<H', b, pe+6)[0]
optsize = struct.unpack_from('<H', b, pe+20)[0]
sec = pe + 24 + optsize
secs = []
for i in range(nsec):
    o = sec + i*40
    name = b[o:o+8].rstrip(b'\0').decode()
    vs, va, rs, ra = struct.unpack_from('<IIII', b, o+8)
    secs.append((name, va, vs, ra, rs))
    print(name, hex(va), hex(vs), hex(ra), hex(rs))

def va2f(va):
    for name, sva, vs, ra, rs in secs:
        if IB+sva <= va < IB+sva+max(vs, rs):
            return ra + (va - (IB+sva))
    return None

# ---- 第二步：反汇编指定函数 ----
md = Cs(CS_ARCH_X86, CS_MODE_32)
for ins in md.disasm(b[va2f(0x4156b0):va2f(0x416500)], 0x4156b0):
    print(f"{ins.address:08x}  {ins.mnemonic:8} {ins.op_str}")
```

> ⚠️ **VA↔文件偏移必须按节表算！**
> 我一开始用 `va - imagebase` 当文件偏移，差了 `0xC00`，
> 反汇编全是乱码，还错误地得出"这程序被混淆了"的结论。

### 4.3 找"谁解析了这个容器"

搜索引用了那个字符串/常量的代码：

```python
# 搜 "001@" 字符串
i = b.find(b"001@")
print("001@ 在文件偏移", hex(i), "VA", hex(f2va(i)))

# 或者搜容器里的其他特征
```

再顺着找**调用链**：谁调用它 → 它调用谁。

### 4.4 排除法：这个容器是干嘛的

本项目在这个解析函数里发现：

- XXTEA 的 `delta = 0x9E3779B9`
- LZMA 解压调用
- 长度前缀读取

**结论：容器 = XXTEA(逐8字节) + raw-LZMA 压的 PE 模块。**

### ✅ 第 4 步的产出

- 容器格式
- 容器解密算法（XXTEA + LZMA）
- 但**还不知道 body 用什么加密**

## 第 6 步：内存扫描——找一个"没名字"的模块

**目的**：本项目的关键转折点——发现 body 加密器**不在主程序里**，而在
**每次拨号动态下载的模块**里。

### 6.1 怎么发现的（推理链）

对比两处数据：

```
容器响应:  001@...$E9747EF1-6849-4F87-957B-3B93E6A90393]
请求头:    Algo-ID: E9747EF1-6849-4F87-957B-3B93E6A90393
```

**Algo-ID 一模一样** → 说明请求是用这个容器里的算法加密的。

### 6.2 这个模块怎么找

它是**内存加载**的，不出现在模块列表里。用**特征码扫描**：

```javascript
// 模块入口处的特征字节（从 PE 文件里读出来）
const SIG = [0x55,0x8b,0xec,0x83,0x7d,0x0c,0x01,0x75,0x05, /* ... */];

function findBase() {
    for (const r of Process.enumerateRanges('r-x')) {      // 只扫可执行内存
        if (r.size > 0x4000000) continue;                  // 跳过超大区域
        let data;
        try { data = r.base.readByteArray(Math.min(r.size, 0x4000000)); }
        catch (e) { continue; }
        const m = new Uint8Array(data);
        outer:
        for (let i = 0; i + SIG.length < m.length; i++) {
            if (m[i] !== SIG[0]) continue;
            for (let k = 1; k < SIG.length; k++)
                if (m[i+k] !== SIG[k]) continue outer;

            // ★ 必须验证 PE 头，否则会误报！
            const base = r.base.add(i - 0x8585);        // 减去入口 RVA
            try { if (base.readU16() !== 0x5A4D) continue; }  // 'MZ'
            catch (e) { continue; }
            return base;
        }
    }
    return null;
}
```

> 💡 **踩坑提醒**：我第一次没校验 `MZ`，扫出一堆**非页对齐**的假基址
> （`0x1a53a1b` 这种），hook 上去毫无反应。
> **加上 `MZ` 校验后**才拿到真基址（`0x3520000`，页对齐）。

### 6.3 特征码从哪来

从**抠出来的模块 PE 文件**里读：

```python
b = Path("algo_module.bin").read_bytes()
fo = 0x400 + (0x8585 - 0x1000)      # 入口 RVA 0x8585 对应的文件偏移
print(b[fo:fo+24].hex(' '))          # 这串就是特征码
```

### ✅ 第 6 步的产出

- 能在内存里定位到动态加载的模块

## 第 7 步：hook 到真正的编码器

**目的**：在模块里找到"输入 XML → 输出 body"的那个函数。

### 7.1 先 hook 入口看编排

模块入口 `+0x8585` 只做分发：

```asm
10008585  push ebp
10008588  cmp [ebp+0xc], 1        ; arg1 == 1 ?
1000858e  call 0x100089c6         ; CRT 初始化
10008593  push [ebp+0x10]
10008596  push [ebp+0xc]
10008599  push [ebp+8]
1000859c  call 0x1000844f         ; → 真正的分发器
```

**把入口和里面几个函数一起 hook**，看谁被调用、参数是什么。

### 7.2 广撒网 hook

```javascript
const OFFS = [0x8585, 0x844f, 0x8245, 0x7a43, 0x6f9e, 0x6b65, 0x6f49,
              0x7808, 0x6d87, 0x6f1b, 0x8298, 0x839f];
for (const off of OFFS) {
    Interceptor.attach(base.add(off), {
        onEnter(args) {
            let s = '+0x' + off.toString(16);
            for (let k = 0; k < 3; k++) {
                try {
                    const v = args[k];
                    if (!v.isNull() && v.compare(0x10000) > 0 && v.compare(0x7f000000) < 0)
                        s += '\n   a' + k + ' [' + ascii(v, 72) + ']';
                } catch (e) {}
            }
            send(s);
        }
    });
}
```

## 第 8 步：造预言机（★★★★★ 最关键的一步）

**目的**：**不要靠读汇编猜算法，直接把它当函数调，喂输入看输出。**

### 8.1 原理

`0x6b65` 是 `cdecl`，`(const char *xml) -> char *hex`。用 Frida 的
`NativeFunction` 就能直接调：

```javascript
function install() {
    const base = findBase();                 // 第 6 步的扫描
    if (base === null) return false;

    // 声明函数原型: 返回指针, 参数是指针
    const fn = new NativeFunction(base.add(0x6b65), 'pointer', ['pointer']);

    rpc.exports.encode = function (xml) {
        const p = Memory.allocUtf8String(xml);   // 在目标进程里分配字符串
        const out = fn(p);                       // 调用！
        return cstr(out);                        // 读返回的 C 字符串
    };
    return true;
}
```

Python 侧：

```python
out = script.exports_sync.encode('<?xml version="1.0" ...?><request></request>')
print(out)   # C853A9968496B3E0...
```

### 8.2 先验证预言机是对的

拿一个**已知的**（输入，输出）对喂进去：

```python
probe = '<?xml version="1.0" encoding="UTF-8"?><request></request>'
out = script.exports_sync.encode(probe)

    print("*** 预言机验证通过 ***")
```

**验证通过才能信后面的实验。**

### 8.3 系统性做对照实验

现在你能**任意构造输入**了。设计一批实验：

```python
cases = []
# 1) 字段值长度递增 —— 看输出怎么长
for n in range(0, 9):
    cases.append((f"field_{n}", f'<?xml ...?><request><a>{"A"*n}</a></request>'))
# 2) 改一个字符
for ch in "ABCZ":
    cases.append((f"char_{ch}", f'<?xml ...?><request><a>{ch}</a></request>'))
# 3) 不同长度
cases.append(("empty", '<?xml ...?><request></request>'))
cases.append(("long", '<?xml ...?><request>' + "A"*64 + '</request>'))

for label, xml in cases:
    out = script.exports_sync.encode(xml)
```

## 第 9 步：静态分析——识别出是什么算法

**目的**：有了结构特征（8 字节分组），再去汇编里**找证据**确认算法。

### 9.1 反汇编编码器，看主循环

从第 7 步知道编码器在 `+0x6b65`，用第 4 步的脚本反汇编：


本项目看到主循环：

```asm

  call 0x10005c78(data, state+0x18)
  call 0x10005e5b(data, state+0x20)
  call 0x10005c78(data, state+0x28)
  ...
  len -= 8; dest += 8; src += 8
```

**每个 8 字节块调用 6 个函数** —— 像是"6 轮操作"。

### 9.2 顺着调用链往里挖

反汇编 `0x5c78`：

```asm
10005ca5  mov ch, [eax + esi]        ; 读一个字节
10005cac  mov cl, 7
loop:                                 ; 逐位展开成 64 位数组
  mov dl, ch
  shr dl, cl
  and dl, 1
  mov [ebp+eax-0xc4], dl
  ...
10005ce4  push 0x40
10005ce6  mov edx, 0x1000c378        ; ★ 一张表
10005ceb  lea ecx, [ebp-0x44]
10005cee  call 0x10005adb            ; 按表做置换
10005cf3  push 0x38
10005cf5  mov edx, 0x1000c0d8        ; ★ 另一张表
...
```

**关键特征：逐位展开 + 按表置换 + 64/56 项** —— 这就是 **DES** 的形状。

### 9.3 把表 dump 出来对比

```python
def dwords(rva, n):
    fo = rva2f(rva)
    return [struct.unpack_from('<I', mod, fo + i*4)[0] for i in range(n)]

print(dwords(0xc378, 64))
print(dwords(0xc0d8, 56))
```

> ⚠️ **注意**：表是 **DWORD 数组**（每项 4 字节），不是字节数组！
> 直接 `read_bytes` 会得到 `58,0,0,0,50,0,0,0,...`，很容易看错。

输出：

```
[58,50,42,34,26,18,10,2,60,52,44,36,28,20,12,4, ...]
[57,49,41,33,25,17,9,1,58,50,42,34,26,18,10,2, ...]
```

**这就是标准 DES 的 IP（初始置换）和 PC-1（密钥置换）** —— 逐项一致。**确认是 DES。**

### 9.4 ★ 血泪教训：不要搜错表

我**一开始搜的是 256 字节的置换表**（AES 那种 S-box），
没搜到，就错误地排除了 DES。

> **DES 用的是 64 / 56 / 48 字节的表，不是 256 字节。**

**正确的做法**：搜"**任意长度的置换表**"（一段区间内每个值出现一次），
不要只找 256 字节的。

### B1. PE 节表解析 + VA↔偏移

```python
import struct
def parse_pe(b, imagebase):
    pe = struct.unpack_from('<I', b, 0x3c)[0]
    nsec = struct.unpack_from('<H', b, pe+6)[0]
    optsize = struct.unpack_from('<H', b, pe+20)[0]
    sec = pe + 24 + optsize
    secs = []
    for i in range(nsec):
        o = sec + i*40
        name = b[o:o+8].rstrip(b'\0').decode('latin1')
        vs, va, rs, ra = struct.unpack_from('<IIII', b, o+8)
        secs.append((name, va, vs, ra, rs))
    def va2f(va):
        for name, sva, vs, ra, rs in secs:
            if imagebase+sva <= va < imagebase+sva+max(vs, rs):
                return ra + (va - (imagebase+sva))
        return None
    def f2va(f):
        for name, sva, vs, ra, rs in secs:
            if ra <= f < ra+rs:
                return imagebase+sva + (f-ra)
        return None
    return secs, va2f, f2va
```

## 结语：五条最值钱的经验

1. **先观察，后反汇编**
   日志 + 抓包能解决一半问题。别一上来就 IDA。

2. **统计学比汇编快**
   "长度都是 8 的倍数" + "块级共享" 这两条统计结论，
   直接定下了"8 字节分组密码"，省掉无数次试错。

3. **能调用就不要猜（★ 最重要）**
   发现 `0x6b65` 之后，最高效的不是继续读汇编，
   而是**把它当函数调**。有了对照组，规律一眼就看出来。

4. **穷举比理解快**
   6 个操作 → 64 种组合 → 10 行 Python 搞定。
   不要去推理"为什么要这样设计"。

5. **验证要有多种独立方式**
   预言机对比 + 真实报文往返 + **让真服务器接受**。
